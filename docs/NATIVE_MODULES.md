# 原生模块与构建

## 形态

DeepTalking 是原生 Android 应用（Kotlin + Jetpack Compose 多模块），入口在 `android-lite/`。WebView 仅作为富文本/公式渲染子系统（`:feature:richtext` 内嵌 KaTeX，KaTeX 资产随该模块打包）。`src/` 是已冻结的历史前端快照（见 `src/README.md`），只作行为参照，不参与构建。

## 关键接口

- 端侧推理（`:engine:ondevice`）：调用方只依赖接口，新增模型 = 新增实现 + 在 `NativeCore` 注册。`LlmBackend` 由 `:core:network` 的 `ResponsesLlmBackend` 实现（远程）；`TtsBackend` 由 `:engine:cosyvoice` 的 `CosyVoiceController.backend` 实现（端侧 CosyVoice3）；`EmbeddingBackend/AsrBackend` 暂为 `null`。
- 朗读播放（`:engine:ondevice` 的 `TtsSpeaker`）：呼叫做朗读者只依赖此接口，具体引擎由 `AppConfig.ttsBackend` 决定——`ondevice` 走 `:engine:cosyvoice` 的 `CosyVoiceController`，`remote` 走 `:engine:remote-tts` 的 `RemoteTtsSpeaker`。唯一的分派点是 `NativeCore.ttsSpeaker(config)`（同时把 `ttsSpeed` 写进引擎），上层与 UI 都不按后端分支。远程失败**不自动回落**端侧（按设计），由已有的「朗读失败」提示暴露。
- Agent 工具（`:domain:agent`）：实现 `AgentTool` 接口并在 `defaultTools()` 注册即可，`AgentLoop` 不变（`ToolRegistry` 对重名工具直接抛异常）。**新增工具时必须同步系统提示词里那份"本会话可用工具"清单**（`prompts/Prompts.kt` 的 `RULE_A_PREFIX`）——清单漏列会让模型以为自己没有该能力；`PromptToolListTest` 会断言清单覆盖全部已注册工具。当前共 9 个：`search_memory`（关键词 / `date`+`timeRef` 按日期 / 给 `category` 即盘点，`limit` 可调）、`web_search`（必应 RSS，`limit` 1–20）、`web_fetch`（只读链接：网页/图片 + 虎扑帖子、网易云歌曲、B站视频的专门解析）、`search`（`platform` ∈ netease/hupu/sticker；sticker=找表情包：一次 3 张、第一张直接发出、其余入库）、`hot_board`（`platform` ∈ baidu/toutiao/douyin/zhihu）、`bilibili_video`（B 站视频唯一入口：`query` 搜视频、`url`/BV 号总结；`HttpBiliVideoSource` 取字幕/官方总结 + `VideoSummaryService` 分块 + 截图墙抽帧，结果本地缓存 7 天；由 `:app` 注入，未接线时不注册）、`memory_write`（`op=update/delete`，update 须 evidence + sourceMessageIds，客户端校验）、`upsert_lorebook_entry`、`send_sticker`（只发不找：`keyword` 必须是库里已有的词；找图走 `search(platform=sticker)`）。平台搜索与热榜各用一个工具 + 显式 `platform` 枚举；都**不需要账号**（不存 cookie、不需要 key）——唯一例外是 `video_summary`：B 站的字幕与官方 AI 总结只对登录态开放，Cookie（`SESSDATA`）由用户在设置页填、只存 `:core:security` 的 `SecretStore`，**不进备份导出、不进数据库/日志**。
- 回合 worker（`:domain:agent` 的 `TurnWorker`）：正文定稿后用**强制 function call**（`tools=[submit_state]`、`ToolChoice.Function`、`reasoningEffort=none`、`stream=false`、`auxiliary`）取回 `dynamicState` / `memberDynamicState`（群组成员，**含各自 `currentTone`**）/ `quickReplies`（**恰好 2 条**：多则留前两条、少则整组弃用并记 note）/ `todos`（`detail` 可空）/ `promiseUpdates`；落盘在 `ChatOrchestrator.runTurnWorker`（待办 create 走 `TodoPolicy.validateTodoCreation`，成员状态走 `applyMemberDynamicState`）。**整轮失败**（请求失败、无结果、解析失败）自动按 1s/2s 退避重试 2 次；仍失败则保留旧状态，聊天页在快捷回应位置显示红色“整理失败·原因，点击重试”，并弹一次“再试一次 / 先这样”；红字只重跑本轮 worker，不重新生成正文。**局部规则拒绝**（待办/约定/动态字段证据或期限不合格等）不重跑整轮，而是记成一条短标签（如 `待办：期限不明`、`当前情绪：证据不符`）写入 `Character.workerIssues`，下一轮 worker 提示词只带最多 8 条短标签，成功后清空。完整长原因仍汇总进 `OrchestratorResult.workerNotes`，写进 `chat.worker` 指标行的 `phase`（`worker-note: …` / `worker-failed: …`）。**worker 已成功给出两条时后台不再跑换位修复；worker 失败或只给出不足两条时仍会修复**（`quickReplyRepairEnabled = config.quickReplyRepair && (!worker.ok || quickReplyCount < 2)`）。静态字段不在聊天回合写入；角色卡编辑器里的“重新生成字段”是独立的手动按钮调用，结果只回编辑框草稿，保存才落盘。
- 记忆（`:domain:memory`）：上层依赖 `MemoryService` 接口。

## 界面与交互

- 配色：`core:designsystem` 暴露 `LegacyColors`（`--bg/--text/--bubble-*/--sidebar/--input-*` 等全部 CSS 变量名，四主题各一套），UI 直接用原值，不再依赖 Material 语义色派生，从根上避免"文字与气泡颜色相近看不清"。
- 应用骨架：顶部 header（hamburger 42dp + 头像 32 + 名称/身份 + 版本徽标 + 缓存面板 ▾ + 主题菜单，高 64dp，随状态栏 inset）+ 左侧抽屉侧栏 **258dp**（**角色 / 设置** 两标签）+ 主聊天区。**缓存面板 ▾** 固定两行中文——**主聊天 / 后台处理**（数据直接读独立指标仓库 `AppViewModel.metrics`；主聊天按 `round` 回溯到本回合第一条 `chat.main` 并加总工具轮，没有用量的行写「缓存 --」）。短期/长期/世界书等一次性后台任务不进缓存面板，保留在设置页「调试信息」的中文逐请求明细里（类型、状态、耗时、tokens、命中/未命中、`contextChars`、`inputChars`、`prefixChange`、`sectionChars`）。
- 消息区：`max-width 56rem` 居中；气泡 `max-width min(84%,560)`、内距 `12px 14px`、圆角 12 + 尾角 4、无阴影、字号 15、行高 1.68；AI 头像 30dp 圆角方块（用户消息无头像）；typing 三点；消息 meta 行（时间 + 30dp 圆形操作按钮）。
- 角色**主动开口**：面板空闲 **60s** 自动触发（随应用可见性暂停/重置），非手动按钮；编辑重发/重新生成会**丢弃后续分支及相关记忆**。
- **热榜开场**（小概率事件，`HotTopicPolicy` + `AppViewModel.armHotTopicTurn`）：每个角色**每个逻辑日（凌晨 2 点换日）只在当天第一个要发请求的回合掷一次骰子**，命中率 10%，上限**每天 1 次、每周 2 次**（自然周，每角色独立）。命中则本轮在 volatile 上下文尾部多一条指令：先调 `hot_board(platform=zhihu)` 查热榜，挑一条与人设合得来的话题自然带入（可叠加在主动开口上）；搜不到就按平常方式回应、不得编造。计数存 DataStore 键 `deeptalking_hot_topic_v1`（JSON：角色id → `{rolledDay, weekStart, weekCount, total}`），**不进 Room、不进备份导出**，所以不牵动 `LegacyMapper`/`BackupService`。
- **待办（独立实体，与长期记忆无关）**（`Character.todos`）：待办不是 `promises`，也不从记忆派生。**新增只有一条闸门**（`TodoPolicy.validateTodoCreation`）：①期限必填且能在对话原话里定位；②用户发起→用户原话含期限与提议；③角色发起→必须附用户应答的原话，且该原话不得是明确拒绝（**同意与否以模型判断为主**，关键词只做一环：`isUserRefusal` 否决明确拒绝、`isUserAgreement` 作正向信号，覆盖不到的说法不否决）。**写入通道有两条**：turn worker 的 `submit_state.todos`（`create` 过上面的闸门，`done`/`cancel`/`reschedule` 走 `applyTodoUpdate`，须引用户原话，改期也要能定位）；记忆整理对用户确认过、期限能由用户原话定位的 promise 调 `TodoPolicy.upsertPromiseTodo()` 补建/更新，角色单方承诺不补，按标题或来源+期限去重。角色编辑页「待办」页签（仅本体）分 `进行中 / 已超时（dueAt < now 派生）/ 已完成 / 已取消`，后两组默认折叠；进行中/已超时行「完成 / 取消」，关闭行「删除」——只是手动兜底。关闭条目保留 `Todo.CLOSED_RETENTION_DAYS`(30) 天（`pruneClosedTodos` 启动维护真删 + 列表防御性过滤）。**无通知投递**：不排期、不弹通知、无通知权限、无 WorkManager；未结束的待办与周期性约定由 `Prompts.buildUnfinishedBlock()` 合并进 `【未完成事项】`，角色可在对话里自然提起。`promises` 侧保留「用户确认过」的记忆元信息（`promisePushDecision`/`pushConfirmedAt`/`pushConfirmedDueAt`）；用户确认且期限可定位的约定由记忆整理补成待办，角色单方承诺不补。`todos` 已随备份导出/导入（`BackupService`/`LegacyDtos`/`LegacyMapper`）。
- 世界书条目受 `enabled` 控制：禁用的条目不参与注入（`LorebookMatcher.select` 过滤），与「常驻」互不影响。
- 多模态：用户图片在请求装配时由 `LlmRequest.imageResolver` 解析为 `data:` URL，`buildResponsesInput` 生成 `input_text` + `input_image(detail:auto)` 内容数组。用户主动发送的**贴图**在该轮请求副本中提升为图片一并送入模型（落盘仍保留 `Kind.Sticker` 供渲染）；`web_fetch`/B站封面/Microlink 主图等工具结果若为 `input_text`/`input_image` 数组，则原样作为 `function_call_output` 数组下发（模型可直接看图，而非 JSON 字符串）。
- 表情包（两级库）：**大类 12 个**（`StickerCategory`：开心/无语/生气/难过/害羞/亲密/得意/惊讶/鼓励/疲惫/动物/其他，只做导航与提示词分组）+ **每张一个关键词**（`Sticker.keyword`，≤7 字，模型在入库时看图写下来，发送时按它选）。入库后由视觉模型**只做两件事**：给关键词 + 归大类（`NativeCore.labelSticker`，提示词只要求 `{"keyword","category"}`）。**模型不承担审核**——图片来源由检索源与素材站域名黑名单把关，模型给不出关键词（超时/不支持看图/输出不是 JSON）时用检索词当关键词，图照样入库，面板可手改。找表情走 `search(platform=sticker)`（**一次找 3 张，第一张直接作为这条回复的表情发出，其余入库备用**）：百度图片检索（`BaiduImageSearch`，关键词自动拼「表情包」，素材站域名黑名单过滤；**请求必须带 `BAIDUID` cookie**——自带 `BaiduCookieJar` 并在进程内预热一次 `https://image.baidu.com/`，不带时百度稳定回 `antiFlag` 整页拦掉，被拦会清掉旧 cookie 重新预热重试一次；**按页取** `pn=page*rn`，全部撞库就自动翻下一页，每页 8 张候选、一次最多入库 3 张）→ 下载（带 Referer；失败记录 HTTP 码 / 超体积 / 超时）→ 压到 384px/120KB（`MediaStore.saveStickerBytes`）→ 视觉起关键词和归类 → 写进角色库（`source=web`，`origin` 取 `replaceUrl` 里的真实来源页，没有再退 `fromURLHost`；百度的 `fromURL`/`fromJumpUrl` 都是 `ippr_` 混淆串，不存）。`send_sticker` 只负责按 `keyword` 发一张（同关键词多张随机）；未命中或空库时错误里直接指路先 `search`，老习惯传 `query` 会被明确重定向。工具结果另带一行给用户看的 `stickerNotice`（「表情库 +1：无语（共 13 张）」/「没找到表情：…」），渲染在回复气泡底部，**不进 content、不进下一轮请求**。**不设张数上限**（加多少、删哪些由用户自己维护）。失败会带一句可转述的原因（搜索为空/候选都下载失败/入库失败/搜到的都是已有的），模型据此如实回复而不是假装加好了。旧数据零迁移：`keyword` 的 JSON 键仍是 `tag`，`category` 缺失时按老标签推断（`StickerCategory.of`）。**群组不启用表情**（`isEnabled` 直接排除 `isGroup`；群组不维护表情库，也不做跨角色共享池）。面板按大类分组并带「全部 / 各非空大类」tab（点 tab 只看该类），长按表情可改关键词/换大类/删除/看大图；长按对话里的图片可「收进表情包」（`AppViewModel.collectSticker` → `MediaStore.saveStickerFromRef`，相对 key/绝对路径/`file://` 统一解析）。图片灯箱走 `Dialog`——不能直接摆在 ChatScreen 的 Column 里，否则会被排到输入栏下方永远看不见；手势是标准看图那套（缩放钉住手指、放大后平移夹在边界内、双击 1x↔2.5x、点一下或 × 关闭），数学在 `MediaZoom` 里并带单测。
- 对话循环（`AgentLoop`/`ResponsesLlmBackend`）：`AUTO` 相工具可用、**工具轮只执行工具并继续**（同轮正文丢弃），`FINAL` 相无工具（`toolChoice=Auto`、`reasoningEffort=none`）且空回合在同一循环内最多重试 2 次、保留已累计工具往返；工具轮达 `MAX_TOOL_ROUNDS`（按模型响应计）直接转 FINAL（`MAX_TOOL_CALLS` 目前无判定点），**同一条响应里的所有 `tool_calls` 都在本轮执行并各配一条 `function_call_output`**；抢救顺序 `extractResponsesText`/内嵌 `reply` JSON（含 reasoning 项）/`extractAnyResponseText`；带 180s 硬超时 + 60s 流式空闲中断（辅助调用 90s）；请求历史 = append-only 的 `instant` 窗口整窗（不再请求侧 `takeLast(60)` 滑窗）；主调用输出纯文本 + 末尾 `【语气】` 行（`ToneText`），`<MEM_UPDATE>` 只在显示层剥离（内容不进入任何状态）；`styleViolations` 写回消息供下一轮的「本轮写法」回顾；`web_search_call.*` 事件经保留状态 chunk 上报为活动提示；启动/导入时静默修损坏头像（`autoRepairAvatars`，含重试 `avatarRepairPending` 项）。正文之后由 `TurnWorker`（强制 `submit_state`）补动态状态/快速回应/待办/约定；静态字段不在聊天回合写入。`ResponsesLlmBackend` 支持 `prompt_cache_hit/miss_tokens` 与 `input_tokens_details.cached_tokens` 两种缓存字段、缺 Key 抛清晰错误、`reasoningEffort` 白名单兜底、Chat-Completions `choices[].delta.content` 流式兜底。
- 注入顺序：世界书按 **常驻优先 → `order`（默认 100）→ 最近更新（`updatedAt` 新的在前）→ 名称（中文 `Collator`）** 排序后按字符预算挑选；预算装不下的条目**跳过、继续尝试后面的短条目**（不再"遇到长条目就停"——旧行为下一条 600 字的常驻条目就能把后面全部挡死），只有单条自身超预算才截断；共享书与成员书合并时按 `id`（空则 `name|content`）去重；命中记 `mentions` 并刷新 `lastMentionedAt`（容量排序的活跃时间来源）。
- **DoH 解析（绕过 DNS 劫持）** `DohDns`（`:core:network`）：部分运营商对特定域名劫持明文 DNS（对 `opencode.ai` 返回无法连接的假 IP），而 Chromium 因内置 Secure DNS 不受影响、OkHttp 走系统 DNS 受害。故给所有 HTTP 客户端（`ResponsesLlmBackend`、`HttpWebContentProvider`、`testApiConnection` 探针）装上同一个 `DohDns`：按 RFC 8484 wire-format 走 DoH，默认**阿里 AliDNS**（`dns.alidns.com`，bootstrap `223.5.5.5/223.6.6.6`）、失败兜底**腾讯 DoH.pub**（`1.12.12.12/120.53.53.53`），DoH 端点用固定 IP 自举（SNI 保留）；A 优先、带 TTL 缓存；任何失败回退 `Dns.SYSTEM`（不受限网络无感知）。设置页「加密 DNS 解析（DoH）」开关 + 提供方选择（`AppConfig.dohEnabled`/`dohProvider`，默认开 + 阿里），策略经 `NativeCore.currentConfig()`/`applyDohPolicy` 实时刷新。
- 语音朗读（端侧 CosyVoice3 或远程服务器，链路搭建见 `docs/REMOTE_TTS.md`）：设置页可下载模型（ModelScope，Q4_K_M GGUF ~630MB + ONNX 前端 ~253MB）；导入**任意音频文件**（mp3/m4a/wav…，不限时长，`AudioLoader` 流式解码并自动截取 ~3s 最清晰人声片段）生成音色，可选填「参考文本」（仅零样本用，instruct 模式会忽略，一般留空）；音色可命名/重命名/删除并保存到列表（`VoiceStore`，内置「内置音色 1/2」，来自 `assets/voices/sample_1/2.wav`）。**朗读气泡**：AI 气泡的「朗读」按钮有状态反馈——合成中显示进度圈 + 实时秒数、播放中变停止键、完成短暂 ✓ 后回到喇叭；点击正在朗读的气泡即停止；**同一时刻仅一个合成，新请求会抢占（停止）旧的**（原生 `cosyvoice_request_stop`）。合成前先 `extractSpeechText` 去掉 `（）/()` 动作与 `【】`/Markdown 标记只留台词；语气指令**不再额外调用 API**，直接取角色动态字段 `currentTone`（模型每轮更新、写成朗读播报指令），以 `instruct` 模式合成。**群聊**：显示层用 `ChatMessage.segments`（`parseGroupSpeechSegments`，一条消息多个气泡）；朗读用另一条路径 `extractSpeechSegments`，按 `成员名：台词`（台词直接写、不加引号包裹；动作写全角括号）把回复切成逐发言人片段，每段取该成员 `memberDynamicState.currentTone`（由 turn worker 写入，为空/成员缺失时回退群组 `dynamicState.currentTone`），逐段合成后拼接为一次播放（仍用同一参考音色）。`extractSpeechText` 会一并剥掉 `「」『』《》〈〉` 这类**引用/书名记号**（只念被引用的文字本身）。自动朗读新回复同样走此流程。同一音色的 prompt-speech GGUF 与派生的 prompt/TTS 上下文会缓存复用（换音色或释放引擎时失效），避免每次朗读重复加载。设备需 arm64（APK 含 `libcosyvoice/libggml*/libonnxruntime/libomp` `.so`）。
- 语音朗读·远程引擎（`:engine:remote-tts`）：设置页把「朗读引擎」切到「远程服务器（电脑）」后，朗读改由 PC 上的 `cosyvoice-server --api` 合成，手机只收 PCM 边收边播（首音延迟与质量由 PC 决定，不再受手机 CPU 限制）。请求映射：`input`=台词、`voice`=服务端音色名、`instructions`=该发言人的 `currentTone`（非空即 instruct 模式，与端侧语义一致）、`speed`=`ttsSpeed`、`model`=`--served-model-name`；`response_format=pcm` 返回 24kHz 单声道 16-bit LE，直通 `PcmOutput` 无需解码，也不依赖服务端 FFmpeg；**`stream:false`（非流式）**——流式下服务端边生成边吐、手机边收边播，PC 生成慢于实时就会饿死播放缓冲（实测游戏占卡时一句 3.5 秒的话要 326 秒）；非流式一次性返回整段，且走的是与端侧同一个入口 `cosyvoice_tts_instruct`。**音色两端共用**：`voice` 留空时取**端侧当前音色**的文件名（去 `.gguf`），服务端以同名注册即两家同音色（`NativeCore.remoteTtsConfig` 负责解析）；App 的音色下拉直接列端侧音色（显示端侧名 + 服务端文件名），并按服务端返回的清单标注「服务端未注册/仅服务端」（API 模式从 `/healthz` 的 `voices` 取，WebUI 模式从 `/speaker` 取）。**音色同步（双向）**：服务端的 `GET /v1/voices` 返回稳定 id、显示名、大小和 FNV 指纹；手机拉取后按 id 对齐，手机有电脑没有就上传，电脑有手机没有就下载，同名不同音色按手机优先并把另一端改成 `_1`/`_2`，同一 id 但内容不同只报告、不覆盖。名字不同时调用 `PUT /v1/voices/<id>` 把电脑显示名改成手机名；只改显示名，朗读用的 speaker id 不变。服务端把显示名持久化在 `--voice-dir/names.json`。旧服务端没有清单接口时，按钮降级为「只上传」并明确提示；不再假装双向同步。端侧已做过裁剪/编码，故两端是逐字节同一个音色（见 `docs/REMOTE_TTS.md` §8）。**高级选项（两端共用，8 项）**（设置页折叠区，**两个引擎都显示**，同一个值既写给端侧 `cosyvoice_set_generation_config`/`set_chunk_tokens`，又随请求体发给 PC，所以调一次两端一起变；框内带模型元数据默认值 `chunk_tokens 28 / temperature 1.0 / top_k 25 / top_p 0.8 / win_size 10 / tau_r 0.1 / min_token_text_ratio 2.0 / max_token_text_ratio 20.0`，可「恢复默认」；存储里的 `0` 按"未设置"回落到默认值）：`chunk_tokens`（速度/峰值内存）、`temperature`/`top_k`/`top_p`（稳定性与表现力）、`tau_r`/`win_size`（重复抑制）、`min|max_token_text_ratio`（生成量下限/上限；**上限是硬截断**，想朗读更快请调 `speed`，见 `docs/REMOTE_TTS.md` §9.2）；访问口令也在其中（仅远程引擎显示）。flow（扩散步数）是编译期常量（**手机 5、PC 10**），DiT 缓存与 `n_max_seq` 属加载期参数，均不在 App 里。**停止**：远程下取消合成＝断开连接（服务端「客户端断开即尽快停止推理」），故 `cancel()` 与 `stop()` 等价；`PcmOutput.write` 返回 false 时立即取消 HTTP 请求。**寻址**：「查找并测试电脑」一个动作完成"扫本机网段 + 验证连通性"——按**手机自身接口的前缀**推 /24 并发扫 `:8080`（`/v1/models`、`/healthz`、`/ping` 任一响应即命中，多网段交错扫描，短于 /24 的前缀收敛到所在 /24 以免扫蜂窝的大网段），命中即写入地址；切到远程引擎且地址为空时会自动执行一次。**回落策略**：远程失败不自动降级到端侧（按设计），由已有的「朗读失败：…」提示暴露，用户可在设置里切回端侧。

## 数据与迁移

- 数据唯一入口：`:core:data` 仓库层（Room + DataStore）。禁止绕过仓库访问数据库。
- 旧数据导入：**先在旧版（或旧备份 JSON）导出，再在原生「导入备份」里经系统文件选择器一次性导入**（`legacy/LegacyImportService`；原生不读取 WebView 的 localStorage）。`legacy/BackupService` 保留旧 JSON 根结构（`{config, characters, activeCharacterId, activeTheme, version}`）的导入导出，导出时每个角色的会话从聊天表（`ChatRepository`）读入 `memory.instant`，不再依赖 `character.instant`。UI 通过系统文件选择器（SAF）导出/导入备份；**导入为整体替换（先清空再写入，带覆盖确认），按 `decodeImportBytes`（UTF-8→GBK→UTF-8 兜底）解码，并迁移同一天重复事件记忆、恢复 `activeCharacterId`、导入后静默补全并询问迁移**。导入还套用同一套归一化：`ensureMessageSequences` 修补消息/场景序号、非 events 长期记忆按分类去重、群组成员限 8 且过滤空名、未知平台归一到 `custom`、`activeTheme` 白名单、按平台预设重建全部 `platformSettings` 槽、损坏头像回退默认 emoji 并置 `avatarRepairPending`、消息 `styleViolations`/`quickReplyIssues` 按词表白名单过滤；**群组 `segments` 随导出/导入往返**（最多 60 段、空文本丢弃；没有该字段的旧备份/旧消息由界面按正文回退解析，解析不到成员才退回单气泡）；导出 `version` 写 `BuildConfig.VERSION_NAME`（不再是 `"native"`）。
- 每平台配置槽 `AppConfig.platformSettings` 保存非密的 Base URL/模型；API Key 走 `SecretStore` 的按平台键（切换平台互不覆盖）。
- 请求指标：`RequestMetric`（含主对话 `round` 与 volatile 各段 `sectionChars`）由 `MetricsRepository` 存在**独立 DataStore 文件**（`deeptalking_metrics`，`MetricsStore.updateRaw` 原子追加），`AppViewModel.metrics` 直接 `observe()` 它；`AppConfig.requestMetrics` 只作旧备份/WebView 兼容（导入时 `migrateLegacy` 一次性采纳）。备份把指标写成**根级 `requestMetrics` 数组**（所有字段在内，导入时整体替换），旧备份里的 `config.requestMetrics` 仍能读。
- 媒体/表情以文件（`filesDir`）存放（`app/MediaStore`：图片压到 ≤1280px/2MB，表情 ≤384px/120KB），不再以 base64 进库；压缩在透明区填白底，质量按 82→70→58→46→34 降级，选图校验 `image/*`。
- API Key 与远程朗读口令存 `:core:security` 的 `SecretStore`（Keystore），设置页只显示脱敏状态。导入/导出时的**备份密码输入框为明文**（仅用于本次加解密，不保存）；导出把密钥加密成根级 `secrets`（PBKDF2-HMAC-SHA256 + AES-256-GCM），导入输入同一密码解密，密码错误不落盘、不修改当前密钥。旧备份没有该段时保留当前密钥。

## 记忆维护任务

每轮后台执行（`BackgroundTasks.scheduleTurn` → `runMemoryMaintenance`）；**各任务互不排队、也不设并发上限**（`BackgroundTaskQueue` 去掉了共享锁：一次补课不再把场景/世界书/快捷回复堵在后面），均可用假后端单测。**短期提取与长期分析仍有数据依赖**：`shortTerm` 满 40 时，分析要等短期提取成功产出条目后才能消费；但 `instant` 在提取请求发出后已经提交为最后 20 条，不等分析、不受分析阻塞。

- **自适应重要度** `selfLearnMemoryImportance`（`:domain:memory`）：30 天内被使用过的记忆按 `usageCount/2` 升权（封顶 +3）；userProfile/habits 45/90/180 天未召回逐档降到 -3（只降权不删除）。召回时累计 `usageCount`/`lastUsageAt`。**记忆衰减/淘汰** `applyMemoryDecay` 同样在维护任务里执行。
- **自动写入校验**（`MemoryEvidence`）：`isValidAutomaticMemory` 校验模型自动写入的 `longTerm` 的 category/subject/证据/角色规则；promise/dynamic 的来源按 `resolvePromiseSources`/`resolveDynamicStateSources`（含 `current_response`）解析；语义冲突写入 `LongTermMemory.conflicts`/`conflictedAt`，由 `resolveMemoryConflicts` 在**长期裁剪路径**（含后台 `upsertLongTermMemory`→`pruneLongTerm`）即时裁决（`memory_write` 的 `op=update` 会把**旧值文本**记入 `corrections`（旧版存档里 `before` 是对象快照，读取端两种形态都兼容）并清空冲突）。主回合不写记忆；turn worker 的 `dynamicState`/`memberDynamicState` 经 `cleanFieldValue`/`parseRelativeText` 与来源校验后落盘，长期记忆保留 `participants/location/arcOf/arcStage`。
- **序号与修订**：每条消息落库带单调 `sequence`（`ensureMessageSequences`）；`Character.revision` 每轮与丢弃分支时自增（`discardConversationBranch` 对齐）。**记忆维护按"合并写回"落盘，不再"过期即丢"**：`captureGuard`/`isGuardCurrent`（`revision`+末条消息 ID）只留给**会覆盖用户可见状态**的任务（场景概要、静态补全、动态状态）；**折叠/分析这类只做增量的任务**改为 API 返回后经 `liveCharacter`（从 `:core:data` 实时读最新角色）**合并**——新条目追加到最新列表、只移除刚刚折过的那批消息、分析只丢掉这一趟真正读过的短期条目（`revision` 变动的那条扣回窗口）。所以用户在模型工作的十几秒里又发了消息，**折叠结果照样落地**（旧实现整批判 `TaskStatus.Stale` 丢弃，"聊得越快越不记忆"）。新短期条目的来源按**折叠开始时读到的整批对话**解析，实时窗口只用于合并已有条目；否则请求期间窗口前进会把来源全部过滤成空。
- **正文之后的结构化补写**：主调用只出正文 + `【语气】`，`TurnWorker` 用强制 `submit_state` 补动态状态/快速回应/待办/约定（请求/解析失败自动重试 2 次；仍失败保留旧状态并红字+弹窗）；局部规则拒绝写成短标签带到下一轮提示词。静态字段不在聊天回合写入。后台任务只做记忆维护与文风/快速回应校验。
- **`history` 与 `instant` 是两个独立的东西**：`history` 是 Room `messages` 里 UI 可上划查看的完整聊天记录，只受归档上限影响；`instant` 是模型请求携带的逐字尾段（瞬时记忆窗口），不是 UI 列表，也不是 history 的镜像。折叠只消费 `instant` 的旧前缀，永远不删除、不回滚 `history`；折叠后的 `instant` 直接提交为本次批次的最后 20 条，不保留旧窗口、不与 live 合并。
- **窗口是持久状态（追加式），存档、窗口、补课三件事各自独立**：`character.instant` 是发给模型的逐字历史窗口，由 `AppViewModel.growInstantWindow` 每轮**只追加**它没见过的聊天行、并丢弃尚未落库的合成项（避免回复重复出现）。它**绝不再从聊天存档重建**：旧实现把"存档 ∪ 窗口"并起来回灌，等于把折叠裁掉的消息原样捞回，窗口只涨不缩、折叠永远原地打转。聊天存档（`history`）是另一份独立数据：Room `messages` 表，纯 FIFO，有 `AppLimits.History.ARCHIVE_MESSAGES`(400) 上限，序号用**高水位**（`max(sequence)+1`，不是行数）保证删旧行后仍单调唯一。**请求侧**（`ChatOrchestrator`）直接使用 append-only 窗口，不再 `takeLast(INSTANT)`；折叠是唯一裁剪点。导入时若窗口低于低水位 `INSTANT_TRIM_FLOOR`(20) 而 `history` 足够，`LegacyImportService` 会用 `history` 尾部重建窗口（修复旧版/失败回合留下的单条合成回复），不会把坏窗口带进新设备。
- **短期窗口同样只追加**：`addShortTermMemory` 只 append（近似合并只看队尾 `SHORT_TERM_MERGE_WINDOW`(5) 条），`MemoryServiceImpl.applyTurn` 也不再对短期做 `dedupe+trim`——压缩只属于折叠那一轮，否则注入块会在稳定期中间变化、缓存前缀无谓失配。
- **不再长度截断**：短期记忆正文（`addShortTermMemory`）与长期记忆 value（`upsertLongTermMemory`）不再按字数截断；长期记忆也不再按 `LONG_TERM_PER_CATEGORY` 数量淘汰（`pruneLongTerm` 默认无上限），仅保留 `applyMemoryDecay` 的时效遗忘。
- **失败退避与第三次提示**：抽取/分析任务带 `scheduleMemoryRetry`/`canRunMemoryTask` 指数退避，避免失败热循环；失败数 ≥3 且该轮尚未应答时，右上角显示红色可点击的“短期记忆生成失败 / 长期记忆生成失败”，点击立即重试。抽取失败时保留完整提取请求（`ExtractionRetryStore`），重试直接重发这个请求，不再从已经折叠的 `instant` 或 400 条 `history` 重新取批次；分析失败不消费 `shortTerm`，按原批次重试。用户点过任一按钮后把 `extractionPromptAcked` / `analysisPromptAcked` 持久化到 `Character.counters`（随备份导出/导入）；成功后计数清零并复位 ack。世界书仍由 `LorebookRetryStore` 在 3 次失败后询问“重试 / 忽略”，弹窗点外部/返回键只关闭 UI，只有显式「忽略并丢弃」才丢批次。
- **旧会话一次性补课（先弹窗确认 → 分批、阻塞、一次跑完）**：`BackgroundTasks.migrateOversizedWindow`（`runInitialMemoryMigration` 为其别名）对超大窗口**分批**折叠——每批最旧的 `INSTANT`(60) 条，折完只丢这批，直到回到正常范围。启动时 `AppViewModel.checkOversizedWindowMigration` 发现 `hasOversizedWindow`（窗口 > `INSTANT_MIGRATION_THRESHOLD`(120)）先弹**确认框**（几个角色、共多少条、预计几分钟、明确"聊天记录一条都不删"，含「以后不再询问」勾选，键 `deeptalking_memory_window_migration_skip_v1`），确认后才弹**阻塞式**进度框（进度、失败原因、重试），期间不可操作；「稍后」= 本次不再问、**下次启动再问**；「以后不再询问」= 之后不再弹窗，积压交给每轮后台的补课通道（照跑，只是不打扰）。每轮折叠前也会判一次，超阈值就走这条通道而不再走正常整窗折叠。
- **场景概要** `summarizeScene`：场景切换或超过 `Scene.SPAN`(12) 条消息且 ≥6 条时，压缩为一条 `scenes`（保留最近 `Scene.RETAIN`(8) 条，**注入只取最近 1 条**；`Scene.SUMMARIES` 为保留常量）。**场景标识取当前地点**：群组读 `groupSharedDynamic.currentLocation`、单角色读 `dynamicState.currentLocation`（`sceneLocation`），空则记「未说明」——读错字段会让群组 key 永远停在「未说明」、地点变了也不触发。**输入带时间**：拼一个 `【时间基准】`（当前本地时间/时区/ISO/逻辑日，与 volatile 同款）放在规则与转录之间，转录每行前面标该条消息自身时间 `yyyy-MM-dd HH:mm（逻辑日 YYYY-MM-DD 时段）`，无可用时间戳的消息标「本条时间未知」；提示词要求日期只能依据给到的时间写、无时间标注的消息不得编日期。游标存 `character.sceneState`（`key`/`startCount`/`startSequence`/`messageCount`，按消息 `sequence` 推进）。
- **世界书整理** `consolidateLorebook`：**跟着短期抽取走**——排在长期分析**之前**，读的正是本次折叠刚产出的那批短期条目（外加内存里上次失败遗留的那批），所以条目在被分析消费掉之前就已经进过世界书；`BackgroundTasksTest` 的三条用例分别覆盖"提取批当轮被整理""失败批不靠新提取也会被重试""连续失败后交给用户"。提示词把现有条目的**完整内容**给模型（最近更新的 `LOREBOOK_EXISTING_FULL_ENTRIES`(12) 条、累计 ≤`LOREBOOK_EXISTING_FULL_CHARS`(6000) 字；其余条目只给名字+关键词并注明"本轮不要更新此条"——正文为空的"待补充"条目内容长度为 0、不占预算，因此总能被完整列出，整理任务因此**可以按名字把用户新建的空条目补上**）。要求"仍有效的原文必须保留 + 新事实，**重新总结成一条去整条替换**旧条目（允许变短）、一条只讲一件事、**目标 300 字 / 硬上限 400 字**"。模型返回的条目**逐条校验**：`sourceShortTermIds` 对不上、名字或内容为空的**跳过**并在请求日志里写明条数（锚不住来源，只能丢）；**超过 400 字的不丢也不截断，而是把原文退回给模型「打回重写」一次**（要求压到 300 字内、保留原意），重写后仍超才放弃并记录原因，**其余条目照常入库**——"一条超长就整批打回"会让世界书永远更新不上；结构性问题（JSON 解析不出、缺 entries）才算整批失败。**写回只动世界书**：不再因为"运行期间角色版本变了"整批作废（`revision` 守卫已从这个任务移除），条目逐条并进当时最新的列表（`upsertLorebookEntryForCharacter`，人工维护条目仍受保护），最终由 `mergeCharacterChanges` 把世界书按条目 id 三方合并进最新行——所以它跑的那几秒里你发的消息不会再把它作废，它也不会回滚你的记忆改动。失败的那批**留在内存**（`LorebookRetryStore`）由下一轮维护与新的批次一起重试，连续 `DEFAULT_MAX_ATTEMPTS`(3) 次后弹窗询问「重试 / 忽略」（同一批只问一次；忽略即按用户意愿丢弃并写一条 `status=note` 说明丢了几条）。**每趟都留痕**：以 `status=note` 记录"本次整理写入 N 条（来源 M 条短期记忆），跳过 K 条：原因…/ 世界书已满，归档了最久未活跃的 N 条：名字…"，"世界书怎么没长"与"这条设定怎么没了"在设备上都能查。写后本地 `dedupeLorebookWithArchive` 兜底（同主题只保留**更新**的那条，不再拼接内容；被替换的旧条目写进 `lorebookArchive`，可恢复，不会像用户删除那样消失），随后按**容量规则**分包：只有本批新增放不下时才归档**最久未活跃**的 `ai` 条目，数量 = 溢出量且单次 ≤ `EVICT_MAX_PER_PASS`(4)（`LorebookStore.archiveToFit` → `Character.archiveOldestLorebookEntries`，活跃时间 = `max(lastMentionedAt, createdAt)`，排序 活跃时间 ↑ → 命中次数 ↑ → id ↑）；**人工维护 / 常驻条目豁免**且不计数，可淘汰池空了就只写放得下的部分、其余下次再写（note 说明）。归档与新增/更新在**同一次返回的 `Character`** 里提交，失败什么都不变。`misses` 字段仅为存档兼容保留，不参与任何判定。**`alwaysActive` 是三态**：模型明确写 true/false 才算回答，**漏写该字段时保留条目原值**（以前一律按 false 处理，模型漏写就把用户的常驻条目默默关掉）；常驻上限 `MAX_ALWAYS_ACTIVE`(6) 对"把已有条目提升为常驻"同样生效（`resolveLorebookAlwaysActive`：已常驻的条目不会被一次不含该字段的更新降级，超限的提升则保持关键词驱动），且**超限只是降级、绝不整条丢弃**。
- **长期记忆只增不删（不再做 LLM 整合）**：原生**已移除**长期记忆的 LLM 整合（旧实现按 `CONSOLIDATE_TRIGGER`(24) 把长期条目交给模型找"重复"并合并——它会改写 `value` 并删除被并入条目，把不同事件/关系条目越并越短、造成不可逆的记忆丢失，故整块删除，含 `MemoryTaskKind.Consolidate` 与 `CONSOLIDATE_*` 常量）。写入路径只做**精确 key（事件另加"日期+时段"同一性）合并**：`upsertLongTermMemory` 精确 key 命中即更新、未命中一律新建（**不再按近似 key 折叠**，避免措辞相近的不同事实被覆盖）；短期 `addShortTermMemory` 在事件同一性 + 内容 bigram 相似度 ≥ `NEAR_DUP_SIMILARITY`(0.72) 时并入。长期记忆**无数量上限**，只由 `applyMemoryDecay` 做时效遗忘。
- **两个窗口都靠"消费即丢"消化，绝不按位置提前截断**：短期窗口里低水位之上的那一段（每批最多 `ANALYSIS_BATCH`(40) 条）交给分析，成功后**原样丢掉这一批**，最新 `SHORT_TERM_TRIM_FLOOR`(20) 条留作上下文；**没有任何逐条"已分析 / 已扫过"标记**。`instant` 同理由折叠消费它真正读过的那批消息（正常通道读**整个窗口**、之后保留最新 `INSTANT_TRIM_FLOOR`(20) 条作原文上下文；补课通道读最旧的 60 条、直接丢掉），**绝不"到高水位就保留最新 20 条"**。触发点：`shortTerm` 低水位之上攒够 `SHORT_TERM - SHORT_TERM_TRIM_FLOOR`(20) 条 → 分析一趟 → 落回 20；`instant` 满 `INSTANT`(60) → **正常通道发送整个窗口**（60、61、62 条都发，**绝不先砍成正好 60**）→ 落回最新 20。抽取侧**不要求模型点名消息 id**、**没有"连续覆盖前缀"约束**：模型把整段窗口压成按"日期+时段"划分的事件摘要，**原话证据由客户端自己采**（窗口里落在该事件同时段的用户消息逐字挂成 `userEvidence`/`sourceRoles`），一条 id 对不上不再作废整批；重复靠**提示词注入当前短期条目**压。分析侧保留**逐条容错**（单条 longTerm 校验不过只丢该条）、**ack 宽容**（只承认本批被点到的 id，缺的下轮再送、混入的忽略）、**截断抢救** `salvageAnalysisReply`；短期→长期的取证链**锚在短期条目上**（`sourceShortTermIds` → 该条目携带的 `userEvidence` 必须逐字命中 `evidence`），模型编造的消息 id 会被**重锚定到命中的那条原话**，不再导致丢弃。后台请求**显式**带 `max_output_tokens`(`AppLimits.Api.AUXILIARY_MAX_OUTPUT_TOKENS`(8192))：分析的回复最长，用服务端默认时会被截断、整批作废。失败原因写进 `counters.analysisLastError`（随存档导出、成功后清空），不再静默；**后台调用失败还会在请求日志里留一条 `status=failed` + 真实原因**（`onAuxiliaryFailure`（→ `recordAuxMetric`），设置页"调试信息"复制出来就能看到）；瞬时失败（断连/超时/429/5xx）在 `BackgroundTasks.completeDetailed` 里按 `ApiRetry` 退避重试 3 次（1s/2s/4s，和聊天一致）。短期的紧急上限 `SHORT_TERM_HARD_CAP`(80) 只在分析持续失败时生效并写明原因，**窗口侧不再有紧急丢弃**（超阈值的窗口归补课通道）。
- **按日期召回**（`search_memory` 工具，原生新增）：模型依据上下文里的时间基准，把用户口语日期（"九号晚上""三号""上周五"）换算成 `date`(YYYY-MM-DD) 或相对说法填 `timeRef`；工具按「日历日**或**逻辑日（一天从 02:00 起算）」匹配，**优先返回那天的原始对话**（`character.instant`，最完整），再补当天 `shortTerm` 与 `longTerm`，可用 `slot` 限定时段、`memberName` 限定成员。用于补足"关键词检索匹配不到口语日期"的缺口。
- **空字段补全** `autoFillStaticFields`：启动时静默补齐为空的静态字段（最多 3 个），只补空、绝不覆盖；单角色与**群组成员**都补（成员补全带群组上下文）；退避用 `staticFillMeta`（成功清零，失败 5→30 分钟指数退避，无失败冷却 24h）。
- **一次性迁移** `migrateWorldLore`（旧 `description`/`background` 里的世界观拆成世界书条目，可选精简原文，标记 `lorebookMigratedAt`）与 `remapFields`（旧字段结构重排，标记 `fieldsMigrationVersion`）与 `repairMemories`（旧数据存量记忆的确定性修复：短期**只按内容近似去重**（不再按"日期+时段"同一性合并，避免丢掉同一时段的不同节拍）、长期按精确 key 分类去重，并**按 `sourceMessageIds` 逐位重建 `sourceRoles`/`userEvidence`**（修复历史"毒丸"条目；无法确定 role 的来源直接剔除，但绝不会把来源清空），标记 `memoryRepairVersion`(3)；无需 API Key，启动/导入后由 `NativeCore.runMemoryRepair` 执行。**另外「价值观」「关键过往」两个基础设定字段已删除**（与性格/背景重叠）：旧行由 `core:data` 的 `RetiredStaticFields` 在**读取时**并入「性格特征」「背景故事」并摘掉退休键（`CharacterRepository.decode` 前缀一步），旧备份由 `LegacyMapper` 同样合并——不需要迁移任务、也不需要"跑没跑过"的标记。**修复/迁移一律跑在 `Dispatchers.Default`/`IO` 上**（`viewModelScope.launch` 默认是主线程；O(n²) 去重放主线程会 ANR，且因 `memoryRepairVersion` 写不进去而每次启动重跑，表现成"点开就卡住然后闪退"）
- **世界书一次性重写** `BackgroundTasks.rebuildOversizedLorebook`：把内容超过 `Lorebook.CONTENT_CHARS`(400) 的 **AI** 条目（`needsLorebookRewrite`，根角色与成员书都算）逐条交给模型，要求"只用原文已有信息、按主题拆成 1~3 条、每条只讲一件事且 ≤400 字、沿用原文专有名词"，结果**原地替换**原条目（第一条保留原 id，注入/命中记录不丢）；拆分后按全局 200 收敛（最久未活跃的溢出进归档），用户手写条目既不发送也不改动；重写结果里任一条**超过 400 字则本次放弃、原条目原样保留**（留待重试），同样不截断。启动时 `AppViewModel.askLorebookRebuildOnce` 检测到这类条目就弹一次确认框（「开始整理」/「稍后」；没有 API Key 时不问），跑完自然不再弹——新写入已被 400 字上限约束，只有**旧数据/旧备份导入**才可能再次触发；失败保留已完成部分、可重试。
- **启动弹窗一次只弹一个**：`AppViewModel.continueStartupPrompts` 把「历史窗口迁移 → 记忆清理 → 世界书重写」串成一条链，每个确认框结束后才轮到下一个（此前清理弹窗与世界书弹窗会同时出现两层、且窗口迁移弹窗会让清理弹窗整轮漏掉）；每个弹窗在本次运行只问一次，「稍后」下次启动再问。
- **后台写回只改自己动过的字段**：`NativeCore.persistMemory(original, updated)` 走 `CharacterRepository.mutate(id)`——在 **per-id 锁**里重读最新行，再用 `mergeCharacterChanges` 只并入本趟确实变化的字段。折叠/重写要跑几秒，整行回写会把期间并发写入的其它内容悄悄回滚。
- **记忆整理与图片整理是两个独立的一次性流程（都不截断）**：启动时 `AppViewModel.checkMemoryCleanupPrompt` 只在「某角色短期记忆超出高水位 `SHORT_TERM`(40)」时问「整理记忆」（键 `deeptalking_memory_cleanup_skip_v1`；文案显示"短期记忆现有 N 条（上限 40）、其中 M 条待消化、会自己跑到 20 条左右"，其中 M 只算**超出 40 的部分**，20~40 的正常窗口不算待消化）。确认后 `drainShortTermBacklog` 只处理 `size > SHORT_TERM(40)` 的角色，把积压消费成长期记忆（**一次整窗折叠即收敛**，每次最多 `AppLimits.Memory.CLEANUP_BATCHES_PER_RUN`(1) 批），并把 `deeptalking_memory_cleanup_pending_v1` 置位：之后**每次启动**再跑 1 批、**空闲每分钟**跑 1 批，直到回到高水位以下才清除标记——同一批积压**只问一次**，**不截断任何内容**（未消化完的条目永不丢弃）。单批走 `BackgroundTasks.drainMemoryBacklog`（分析一趟 + 世界书/场景维护），返回 `DrainOutcome(character, progressed)`；无进展时把 `counters.analysisLastError` 落盘并在提示里显示原因，不再空转。**图片是另一个弹窗**：`checkImageCleanupPrompt` 只在有超出保留窗口 `AppLimits.Media.IMAGE_RETENTION_MESSAGES`(60) 条消息的旧图片时问「整理图片」（新键 `deeptalking_image_cleanup_skip_v1`），确认后只跑 `NativeCore.pruneOldMessageImages`，把旧图**原地压成缩略图**（`Media.THUMBNAIL_DIMENSION`(384)/`THUMBNAIL_QUALITY`(60)；附件引用不变、聊天文字不动，界面照旧显示、只是老图变低清，**不再出现破图**；孤儿 sha 文件仍会删除），**不读也不整理短期记忆**、不触发分析、不改注入前缀。两个弹窗串行出现（记忆 → 图片 → 世界书整理），确认后都会把启动提示链交给下一步。；另有 `RelativeTimeMigration`（相对时间转绝对日期，标记 `timeParseVersion`；覆盖根角色与**群组成员**的 `shortTerm/longTerm/dynamicState` 及静态字段，基准取各自 `staticFieldMeta`/`dynamicStateMeta.updatedAt`）。启动时（有 API Key 且未勾选"以后不再询问"）由 `AppViewModel.checkMigrationPrompts` 弹`AlertDialog`询问——先"字段结构升级"，后"世界书整理"（含"同时精简原文"勾选）；确认走 `NativeCore.runWorldLoreMigration` / `remapCharacterFields`，"以后不再询问"写入 `SettingsStore`（键 `deeptalking_field_migration_skip_v1` / `deeptalking_lorebook_migration_skip_v1`）。**世界书整理只在检测到目标（`lorebookMigrationTargetCount>0`）时才询问/执行，处理完标记 `lorebookMigratedAt` 后自然不再提醒；`runWorldLoreMigration` 逐角色 `try/catch` 隔离，单个失败不会清零整批，返回 `LorebookMigrationOutcome(success, failed)`。** 注意 `LorebookProposal` 依赖 `@Serializable`（`migrateWorldLore` 把它序列化进 prompt）。**这些写整行角色的任务（补全/迁移/相对时间）在 `NativeCore` 里用同一把 `Mutex` 串行，且 upsert 前按 id 重读最新角色、只覆盖自己负责的字段**，避免互相覆盖标记。新建/导入的实体直接写入 `fieldsMigrationVersion="1.2.0"`、`lorebookMigratedAt=now`，不再反复弹迁移框。

**证据与意图校验**（`MemoryEvidence`）：`hasValidUserEvidence` 要求 `sourceMessageIds` 解析为真实用户消息且 `evidence` 逐字出现。写入路径据此拒绝无据写入：turn worker 的 `dynamicState`/`memberDynamicState`/`todos`/`promiseUpdates`（`ChatOrchestrator.runTurnWorker`，待办 create 再过 `TodoPolicy.validateTodoCreation`；成员 `currentTone` 免证据门）、`memory_write`（`op=update` 的 `evidence` + `sourceMessageIds` 由客户端强制，`short_` 前缀可改短期 `value`/`eventTime`）、`upsert_lorebook_entry`。`todos` 的改期/完成/取消同样要过 `hasValidUserEvidence`（改期再过 `dueAtBackedByEvidence`）。自动写入冲突时 `memoriesSemanticallyDiffer`（token 重叠 <0.35）阻止静默覆盖。短期窗口只由整窗抽取写入，主调用与 worker 都不写。短期记忆在写入时记录 `sourceRoles` 与 `userEvidence`（用户消息逐字摘录），供短期→长期分析在源消息已滚出 `instant` 后仍能校验证据。

**导入数据安全**（`LegacyImportService`/`LegacyMapper`）：导出把**两个独立存储分开写**——`memory.instant` 是高低水位窗口（B），新增的顶层 `history` 是聊天存档队列（A）；导入时有 `history` 就用它当存档、`memory.instant` 当窗口，**没有 `history` 的旧备份**（含 `save/` 下所有历史存档）仍按旧语义把 `memory.instant` 同时当存档与窗口，保证老文件可导。图片**只内联缩略图**（`MediaSource.toThumbnailDataUri`，`Media.THUMBNAIL_DIMENSION`(384)/`THUMBNAIL_QUALITY`(60)），原图只留本机；导入的图片按"不需要质量"重压到 `IMPORTED_IMAGE_DIMENSION`(512)/`IMPORTED_IMAGE_QUALITY`(70)，不再原样落盘（顺带修掉 PNG 一律存成 `.jpg` 的隐患）。旧版备份里 `shortTerm/longTerm.userEvidence` 恒为 `[{sourceMessageId,text}]` 数组、`conflicts` 为 `[{value,evidence,sourceMessageIds,at}]` 对象数组；原生用容错编解码（`SourceEvidenceListSerializer`/`MemoryConflictListSerializer`/`MemoryCorrectionListSerializer`，同时接受字符串/数组/对象）映射到 `SourceEvidence`/`MemoryConflict`/`MemoryCorrection`，避免整角色解码失败被静默丢弃。导入会套用旧版长度/数量上限（`sourceMessageIds`/`evidence`/`participants`/`scenes`/世界书名与内容等），世界书**按全局 200 一次性收敛**（`convergeLorebookCapacity`：本体 + 成员合计，只算 `ai` 条目，最久未活跃的溢出**进归档**而非丢弃），`lorebookArchive` 随导出/导入往返（保留人工/AI 归属），**`todos` 也已纳入导入/导出**（`BackupService` 的 `LegacyDtos`/`LegacyMapper.mapTodos`：缺标题的条目丢弃、未知 status 回退 active），**新版备份恢复原生 TTS 设置/数值**（旧备份缺字段时逐字段沿用当前值；音色路径按文件名匹配本机，不存在就置空），`counters` 的 ack、`workerIssues`、`memoryRepairVersion` 也随备份往返（旧备份缺字段分别默认 false/空/0），`lastReplyDebug`、`requestMetrics` 仍按旧规则处理，`platformSettings` 为空时沿用现值，并在 `ImportSummary.skipped` 里上报无法解析而被跳过的角色数（不再静默）。**导入归一化按多信号加权合并长期事件**：主题/key 0.28、正文 0.38、来源重合 0.24、参与者 0.06、地点 0.04（缺失维度重归一），相反结果/人物/地点冲突一票否决；总分 **严格 >0.70** 才自动合并。仅同一时段但内容不同的条目保持独立；真重复合并保留完整正文和双方全部来源 id（缺 role 也保留 id，不再按时段批量合并或截断）。短期仍按内容相同合并。

## 构建与自检

统一走 `tools/` 下的原生脚本（自动解析 JDK17/Android SDK/Gradle，见 `tools/native/env.ps1`）：

```powershell
powershell -File tools/native-verify.ps1    # 全量自检：静态检查 + 编译 + 全部单测

powershell -File tools/native-build.ps1 -Release -Publish   # 本地出包 + 上传 GitHub Release
powershell -File tools/native-version.ps1 [-BumpPatch]
```

## CI

CI（`.github/workflows/verify-lite.yml`）在 `android-lite/**` 变化时只做**编译 + 与本地自检相同的全部单测**，作为门禁；它**不构建、不发布**任何包（因此 CI 里没有 keystore，也不可能覆盖已发布的 APK）。

**出包在本地**：`tools/native-build.ps1 -Release -Publish` 用本机 keystore 签名构建 release APK、归档到 `apk/DeepTalking-lite-v<版本>.apk`，再用 `gh` 把这个**本地包**创建/覆盖上传到 GitHub Release（tag `v<版本>`）。这样 Release 上的包永远就是本地验过的那个。包名、签名与数据迁移链的稳定是覆盖升级的兼容要求。
